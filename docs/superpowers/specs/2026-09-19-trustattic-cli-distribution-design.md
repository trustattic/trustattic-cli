# TrustAttic CLI — Distribution & Install Design

## Summary

Add a release pipeline so `trustattic` can be installed via Homebrew (macOS),
winget (Windows), or a generic `curl | bash` / `irm | iex` install script —
matching the install experience Claude Code documents at
[code.claude.com/docs/en/quickstart#native-install-recommended](https://code.claude.com/docs/en/quickstart#native-install-recommended).
**GoReleaser** orchestrates the whole pipeline from a single config, triggered
by pushing a semver git tag.

## Goals

- `brew install trustattic/tap/trustattic-cli` works on macOS (Intel and
  Apple Silicon).
- `winget install TrustAttic.CLI` works on Windows.
- `curl -fsSL https://raw.githubusercontent.com/trustattic/trustattic-cli/master/install.sh | bash`
  works on macOS/Linux; PowerShell (`irm ... | iex`) and CMD equivalents work
  on Windows.
- Cutting a release is a single action (`git tag vX.Y.Z && git push --tags`)
  that produces all of the above without further manual steps, except
  winget's PR passing Microsoft's own review.

## Non-goals

- **No self-updating binary.** Re-running the install script, or
  `brew upgrade` / `winget upgrade`, is how users get a new version — no
  background auto-update like Claude Code's native install.
- **No code signing or macOS notarization in this pass.** Unsigned binaries
  may trigger Gatekeeper/SmartScreen warnings, especially on direct browser
  download; less friction via `brew`/`winget`. Signing requires a paid
  developer account/cert — a follow-up, not blocked on here.
- **No submission to `homebrew-core`.** That tap requires an established,
  notable project and a maintainer review process, impractical for a new
  CLI. A dedicated tap repo is the standard alternative for a project at
  this stage.
- **No CI beyond this release pipeline** — the existing gap (no `go build`/
  `go test` CI at all) is a separate, already-flagged follow-up, not
  addressed here.

## Prerequisites: repo visibility and license

`trustattic/trustattic-cli` must be **public**. Homebrew, winget, and an
anonymously-`curl`-able install script all require publicly fetchable
release artifacts; a private repo's releases aren't reachable without
authentication, and neither Homebrew's tap mechanism nor winget's manifest
format are designed to point at private sources. `platform` and `cloudapi`
stay private — only the CLI (a thin, generated API client with no secrets
or business logic) becomes public.

`trustattic-cli` also needs a `LICENSE` file — it doesn't have one today.
`platform`'s license is proprietary/all-rights-reserved, appropriate for a
private backend but unusual for a binary meant to be freely installed
through public package managers. This CLI ships under **MIT** instead —
permissive, the de facto default for Homebrew/winget-distributed CLI tools,
and independent of `platform`/`cloudapi` staying proprietary and private.

## Architecture

A GitHub Actions workflow (`.github/workflows/release.yml`) triggers on
pushing a tag matching `v*` and runs `goreleaser release --clean`, which:

1. **Cross-compiles** `trustattic` from `cmd/trustattic` for
   `linux/amd64`, `linux/arm64`, `darwin/amd64`, `darwin/arm64`, and
   `windows/amd64`.
2. **Packages** each as a `.tar.gz` (Unix) or `.zip` (Windows), generates a
   single `checksums.txt` covering all archives, and creates a GitHub
   Release on `trustattic-cli` with everything attached, using the tag as
   the version and an auto-generated changelog from commit messages since
   the previous tag.
3. **Updates the Homebrew tap**: renders a formula
   (`Formula/trustattic-cli.rb`) pointing at this release's macOS/Linux
   archives and checksums, and pushes it to a new, separate
   `trustattic/homebrew-tap` repo (GoReleaser's `brews:` pipe), authenticated
   via a repo secret.
4. **Opens/updates the winget PR**: renders a winget manifest (three YAML
   files: version, installer, locale) and opens or updates a pull request
   against `microsoft/winget-pkgs` (GoReleaser's `winget:` pipe), pointing at
   this release's Windows archive, authenticated via a separate repo secret.
   This PR is reviewed and merged by Microsoft/community maintainers outside
   our control — it does not block steps 1–3.

The **generic install script** (`install.sh`, `install.ps1`, `install.cmd`)
is hand-written, not generated by GoReleaser, and lives directly in
`trustattic-cli` at the repo root — it doesn't need a release to exist yet,
only for one to exist when it's run. It's fetched straight from
`raw.githubusercontent.com` (no custom domain, no GitHub Pages setup needed):

```bash
curl -fsSL https://raw.githubusercontent.com/trustattic/trustattic-cli/master/install.sh | bash
```

```powershell
irm https://raw.githubusercontent.com/trustattic/trustattic-cli/master/install.ps1 | iex
```

```batch
curl -fsSL https://raw.githubusercontent.com/trustattic/trustattic-cli/master/install.cmd -o install.cmd && install.cmd && del install.cmd
```

## Components

### `LICENSE` (new, repo root)

Standard MIT license text, copyright line for the current year. Referenced
by the Homebrew formula's `license` field and by GitHub's own license
detection (shows up on the repo's main page once public).

### `.goreleaser.yaml` (new, repo root)

Declares:
- `builds:` — the `cmd/trustattic` entrypoint, the five OS/arch targets,
  `CGO_ENABLED=0`, version info injected via `-ldflags` (so `trustattic
  --version` reports the release tag).
- `archives:` — naming convention (`trustattic_<os>_<arch>` (version-free, required for the `releases/latest/download/<name>` install approach below)),
  `.tar.gz` for Unix / `.zip` for Windows, README/LICENSE included in each
  archive.
- `checksums:` — a single `checksums.txt` per release.
- `brews:` — tap repo (`trustattic/homebrew-tap`), formula name, install
  block (`bin.install "trustattic"`), test block (`system "#{bin}/trustattic
  --version"`), homepage/description/license metadata.
- `winget:` — package identifier (e.g. `TrustAttic.CLI`), publisher,
  license, short/long description, the `microsoft/winget-pkgs` repo as the
  PR target, and the release's Windows archive as the installer source.
- `release:` — changelog generation settings (grouped by conventional-ish
  commit prefixes if present, otherwise a flat list).

### `.github/workflows/release.yml` (new)

Triggers on `push: tags: ['v*']`. Single job: checkout (full history, so
GoReleaser can generate the changelog), set up Go, run
`goreleaser release --clean` with `GITHUB_TOKEN`,
`HOMEBREW_TAP_GITHUB_TOKEN`, and `WINGET_GITHUB_TOKEN` in the environment.

### `trustattic/homebrew-tap` (new repo)

Public, minimal — exists purely to hold `Formula/trustattic-cli.rb`
(generated and pushed by GoReleaser; never hand-edited). A short README
explains `brew tap trustattic/tap && brew install trustattic-cli`.

### `install.sh` / `install.ps1` / `install.cmd` (new, repo root)

Each does the same four things for its platform:

1. **Detect OS/arch** — `uname -s`/`uname -m` (mapped to GoReleaser's
   `linux`/`darwin`, `amd64`/`arm64` naming) for the shell script;
   `$env:PROCESSOR_ARCHITECTURE`/`.NET` runtime info for PowerShell — and
   construct the exact archive filename GoReleaser's naming template
   produces for that OS/arch (e.g. `trustattic_darwin_arm64.tar.gz`). This
   is a pure, offline computation — no network call needed to know the name.
2. **Resolve the download URL** — GitHub serves a stable, documented
   redirect for the most recent non-prerelease release's named assets:
   `https://github.com/trustattic/trustattic-cli/releases/latest/download/<asset>`.
   The script builds this URL directly from the filename computed in step 1
   (and identically for `checksums.txt`) — no GitHub API call, no JSON
   parsing, no extra dependency (`jq` or otherwise), and no exposure to the
   unauthenticated API's 60-requests/hour rate limit. A `curl`/`Invoke-
   WebRequest` that follows the redirect and gets a 404 means the
   OS/arch combination isn't in the release — the script checks the HTTP
   status explicitly and errors clearly (naming the OS/arch) rather than
   saving a 404 error page as if it were the binary.
3. **Download and verify** — fetch the archive and `checksums.txt` into a
   temp directory, verify the archive's checksum, abort with a clear error
   on mismatch (never install an unverified binary).
4. **Install** — extract, then place `trustattic` in `~/.local/bin` (or
   `/usr/local/bin` if that's writable and already on `PATH`) on Unix; a
   per-user directory added to `PATH` via the registry on Windows. Print the
   installed version and a one-line "run `trustattic login` to get started"
   hint.

## Error handling

- Any build/package/checksum failure in the GoReleaser job fails the whole
  workflow — no GitHub Release, no tap update, no winget PR. A release is
  all-or-nothing at the GoReleaser-job level.
- A winget PR that fails Microsoft's automated manifest validation is
  independent of the other three artifacts — it just sits open for manual
  follow-up (check its status, push a corrected manifest by re-running the
  winget pipe, or fix and re-tag). It never blocks or rolls back the GitHub
  Release or Homebrew tap update, which are already public by that point.
- The install script fails loudly and specifically: unsupported OS/arch
  names the platform it can't find a build for; a checksum mismatch names
  both hashes; no releases found says so rather than crashing on a nil
  response.

## Testing

- `goreleaser release --snapshot --clean` (or `goreleaser build --snapshot
  --clean` for just the binaries) runs the entire build+package+changelog
  pipeline locally without publishing anything — this is how the
  `.goreleaser.yaml` config gets validated before ever pushing a real tag,
  and how regressions in the config get caught in CI on every PR (a
  snapshot-mode run added to a lint/build workflow, separate from the
  tag-triggered release workflow).
- The install scripts' OS/arch-detection and filename-construction logic is
  a pure function of `uname -s`/`uname -m` (or their Windows equivalents)
  with no network dependency, so it's directly unit-testable: call it with
  each supported and unsupported OS/arch combination and assert on the
  resulting filename (or the "unsupported" error), without mocking anything
  or touching the network.
- End-to-end verification of `brew install`, `winget install`, and the
  install scripts running for real can't happen from this development
  environment (no macOS/Windows, and winget review runs on Microsoft's
  infrastructure) — the first real tag push is the actual end-to-end test.
  Recommend a `v0.1.0` tag as a deliberate first test release once this
  lands.
